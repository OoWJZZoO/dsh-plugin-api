# Design: plugin-api-repo-normalization

> feature_name: `plugin-api-repo-normalization`
> 状态：Stage 2 草案（三轮对抗审查意见均已修订，待用户批准）
> 上游：Stage 0 Goal、Stage 1 Requirements（均已批准，commit 058849e；requirements 在 Stage 2 审查期间 B1.1 一次修订：修复范围扩至私有标识符处置路径）
> 类型：治理/工程规范化（无第三方可见 API 新增）

---

## 1. Overview 与执行模型

本 feature 在一个审计周期内完成「审计 → 登记 → 分批复核」。执行面只在本 feature 的承载 worktree（M6 规划分支），不修改 M4/M5 执行分支的任何文件；对它们的发现项只登记待办（Requirements F3）。

执行链路：

```text
快照审计（静态扫描 + 官方包核验 + 版本核验）
  → 登记文件（报告 + 全部登记表）
  → 分批复核（按域，每批一个获批顶层任务）
  → 复审（重跑扫描 + 全量测试 + diff --check）存量项零未决
```

审计时点与 base 以 Requirements A0.2 锚定：main 处于治理迁移合并前（旧路径 ×9、AGENTS.md §8 旧形态、feature-list §7 缺失），这些作为「迁移项」单独呈列并以外部依赖跟踪（F1/B1.2），不参与「存量项零未决」判定。

### 2.2 人工判定点与处置路径

扫描无法自动定性的命中，按两类处置，逐条写入登记文件并标注判定人与日期：

1. **注释/测试名命中**：改为中立、面向语义的表述，零行为变化（以全量测试门验证）。
2. **运行时私有标识符命中**（例如 `runL4Phase`、`_execRouteP2Diagnostics` 等内部函数名）：二选一处置——(a) 行为保持的重命名（新名称中性，自带全量测试门）；(b) 登记为「已确认技术债」并经人工确认，进入重构窗口建议（A3.3）。不得默认豁免，不得跨过复审悬置（见 §5）。

人工判定还包括：豁免白名单（C0/C1 等）、A1.4 词汇混用点定性（既有契约 vs 本次/后续引入）、A3.2 逐 namespace 豁免论证。

## 4. 修复批次划分（与 Tasks 顶层任务对齐）

每批 = 一个顶层任务 = 一个对抗审查单位（AGENTS.md §3.2）：

| 批次 | 域 | 内容 | 承载需求 |
|---|---|---|---|
| 1 | 背景项 | B1.1 所列 16 处注释/测试名改写（零行为变化）；增强扫描新发现命中的分级处置（§2.2：注释/测试名改写、私有标识符重命名或登记确认技术债）；governance-token-audit 自卫生（现有字面 `'A11'` 改为拼接构造，使测试自身不含字面禁用 token）；迁移项复检（合并后） | B1.1/B1.2、F1 |
| 2 | 身份/世代/终态 | 词汇映射登记（S5①）与 A1.4 混用点定性；A1.1/A1.2 结论登记（S5②） | A1.1–A1.4 |
| 3 | 持久化 | scope 归属表、能力声明补齐与豁免（含 appendMessage 官方语义声明、remote.publish 同键冲突声明、retry 现状明示） | A2.1–A2.3 |
| 4 | API 形状 | 三面映射图 + smell 判据 + 重构窗口建议表；重构建议为**非阻塞知悉**（交付时呈报用户，不等待批准、不新增确认门），负债项未附重构建议不得标记关闭（A3.3） | A3.1–A3.3 |
| 5 | R 类 | 1:1 边界核对（A4.1）；六步判定登记（A4.2，compaction-events / session-title）：**六步逐项结论 + 逐项证据位置指针回填两个 R 包 requirements**（兑现 capability-strategy §10"判定结果必须在 R 类 requirements 中记录、逐项给出证据"），全量证据保留于本 feature 登记文件；版本核验（A4.3） | A4.1–A4.3 |
| 6 | 可见性 | 可见性现状登记与声明缺口建议 | A5.1/A5.2 |

## 5. 失败路径与 guard

- **扫描工具失败**：该检查项记为 `not-audited` 并显式列明，绝不静默当作"零命中"。
- **改写零行为变化**：批次 1 的注释/测试名改写与私有标识符重命名均以全量 `node --test` 全绿为门；任何行为变化即回退并标记缺陷。
- **豁免需人确认**：豁免白名单与人工判定结论必须逐条显式记录；未确认的命中按「待宣布」呈现，且**待宣布项必须在本批次审查前完成人工确认或显式升级（进入重构窗口建议/升级用户裁决）**，不得以"待宣布"身份进入复审（保证 F1 存量项零未决可闭环）。
- **登记不虚构**：每条登记引证据；无法获得证据的条目标 `unverified`，不得写"合规"。
- **跨分支不代改**：M4/M5 指向项只登记待办（F3），批次内不触碰其文件；批次提交 diff 的文件路径不得含 M4/M5 在途文件。
- **版本不动**：批次内任何 package.json 改动不得变更 version / dsh.api（A4.3）。
- **不新增确认门**：A3.3 重构建议呈报为知悉性动作，不阻塞后续批次。

## 6. 验证矩阵

| 门 | 验证 |
|---|---|
| 每批 | 该批任务自测 + `git diff --check` + 阻塞性对抗审查（无未决意见） |
| F1 | 增强扫描存量项零未决 + 全量 `node --test` 全绿 + `git diff --check` |
| F2 | 公开 API 形状 / 事件目录 / 错误分类 / **命名空间 / peerDependency** / 包版本 diff 为空（除批次 1 的注释、测试名与经批准的私有标识符重命名） |
| F3 | 审计报告含 M4/M5 待办登记；批次提交 diff 文件路径不含 M4/M5 在途文件（机械检查） |

## 7. 边界与豁免

- 不实现任何 M6 候选 feature；不修订 `docs/standards/` 分册；不修改官方 DSH 包文件。
- 不重命名已交付的运行时包/行 id；不改公开 API 形状；**不新增目录事件、错误分类、命名空间或 peerDependency**（requirements 非目标第 3 条）。
- 治理迁移合并（B1.2）为外部依赖，不在本 feature 内执行合并，只复检。
- 批次 5 对 R 包 requirements 的追加限于「六步逐项判定结论 + 逐项证据位置指针」，不改写历史验收内容；全量证据以本 feature 登记文件为主副本。
